## Статус

## Контекст

Наша команда разрабатывает PCPulse — приложение для мониторинга производительности ПК с игровым оверлеем и рекомендациями по апгрейду.

**Характеристики проекта:**

- Размер команды: 4 человека.
- Репозиторий: https://github.com/PCPulse/app-conf-project-pcpulse
- Текущее состояние: создано FastAPI-приложение с эндпоинтами GET / и GET /health, подготовлены README.md и CONTRIBUTING.md.
- Опыт команды с Git — базовый учебный. В первой практике команда применяла рабочие ветки, коммиты, push и Pull Request. На практике №2 закрепляем ревью, обработку замечаний и работу с защищённой main. Поэтому выбираем знакомый процесс без дополнительных долгоживущих веток.
- Частота релизов: фиксированного расписания пока нет. Версии готовим по готовности согласованного набора задач после ручной проверки. Слияние отдельного PR в main само по себе не означает выпуск пользовательской версии.
- Требования к стабильности main: изменения должны проходить проверку другим участником до слияния.
- Автоматические проверки CI пока отсутствуют; работоспособность приложения проверяется локально.
- В CONTRIBUTING.md первой практики уже указана стратегия GitHub Flow.

**Проблема:** необходимо закрепить стратегию ветвления, которая позволит:

1. Параллельно работать над кодом и документацией.
2. Проверять изменения перед включением в main.
3. Выполнять требования курса: изменения через PR с минимум одним approval.
4. Использовать понятный процесс без лишних постоянных веток.

## Рассмотренные варианты

### Вариант A: GitFlow

**Суть:** стратегия с основными ветками main и develop, а также ветками feature, release и hotfix.

**Плюсы:**

- Отделяет текущую разработку от стабильной версии.
- Позволяет готовить релиз отдельно от разработки следующих функций.

**Минусы:**

- Требует синхронизации нескольких долгоживущих веток.
- Увеличивает количество операций merge и правил для команды из четырёх человек.

**Подходит ли нам:** нет — для текущего процесса работы дополнительные постоянные ветки и отдельный цикл подготовки релиза не требуются.

### Вариант B: GitHub Flow

**Суть:** main содержит стабильную версию. Изменения выполняются в отдельных рабочих ветках и включаются в main через Pull Request.

**Плюсы:**

- Простой цикл работы: рабочая ветка, PR, ревью, merge.
- Продолжает процесс, использованный в первой практике.
- Позволяет проверять каждую задачу отдельно до включения в main.

**Минусы:**

- Нет отдельной постоянной ветки для интеграции изменений.
- При отсутствии CI стабильность main зависит от ручных проверок и качества ревью.
- Ожидание ревью может задерживать включение готовой задачи.

**Подходит ли нам:** да — стратегия соответствует размеру команды и требованиям курса.

### Вариант C: Trunk-Based Development

**Суть:** небольшие изменения часто интегрируются в основную ветку; рабочие ветки существуют короткое время. В рамках курса интеграция также должна выполняться через PR с approval.

**Плюсы:**

- Частая интеграция уменьшает расхождение веток.
- Небольшие изменения проще проверять и объединять.

**Минусы:**

- Требует дисциплины небольших задач и частой интеграции.
- При отсутствии автоматических проверок увеличивает нагрузку на ручную проверку стабильности основной ветки.

**Подходит ли нам:** нет — на текущем этапе команда закрепляет работу через отдельные ветки задач и ручное ревью, CI ещё не настроен.

## Решение

Мы выбрали стратегию **GitHub Flow**.

**Схема ветвления:**

```text
main:                       ●─────────────●─────────────●
                             \           / \           /
docs/pr-template:             ●────●─────/   \         /
feature/version-endpoint:                     ●───●───/
```

Каждая рабочая ветка создаётся от актуальной main. После выполнения задачи автор открывает Pull Request в main. Другой участник проверяет изменения и ставит approval, после чего выполняется merge. Рабочая ветка удаляется.

На схеме показаны создание шаблона PR и добавление эндпоинта /version. Остальные рабочие ветки проходят такой же цикл.

**Правила работы с ветками:**

1. main содержит проверенную работоспособную версию приложения.
2. Каждая задача выполняется в отдельной ветке от актуальной main.
3. Все изменения main поступают через Pull Request.
4. Перед merge требуется минимум один approval другого участника с правом записи. Автор не одобряет собственный PR.
5. Автор заполняет шаблон PR и указывает воспроизводимый способ проверки.
6. Сообщения коммитов оформляются по Conventional Commits.
7. Обсуждения закрываются перед merge по регламенту CONTRIBUTING.md.
8. После новых коммитов approval сбрасывается; автор запрашивает повторное ревью.
9. Рабочая ветка удаляется после merge.

**Именование веток:**

Формат: префикс/краткое-описание.

Описание пишется латиницей, слова разделяются дефисами.

- feature/ — новая функциональность;
- bugfix/ — исправление ошибки;
- docs/ — документация;
- chore/ — зависимости и служебные изменения.

Примеры:

- feature/version-endpoint;
- bugfix/health-response;
- docs/contributing-rules;
- chore/dependency-files.

**Защита ветки main:**

Используется ruleset protect-main:

- Enforcement status: Active.
- Bypass list: пустой.
- Target branches: Include default branch — main.
- Restrict deletions: включено.
- Block force pushes: включено.
- Require a pull request before merging: включено.
- Required approvals: 1.
- Dismiss stale pull request approvals when new commits are pushed: включено.
- Require conversation resolution before merging: включено.
- Require status checks to pass: выключено до появления CI.
- Require linear history: выключено.

В настройках репозитория включено Automatically delete head branches.

### Административный доступ и ответственность

Репозиторий принадлежит организации PCPulse. Среди участников команды настройки безопасности, защиту main и ruleset protect-main может изменять только Чувильчиков Кирилл.

Остальные участники изменяют код и документацию через рабочие ветки и Pull Request. Для выполнения этих задач административные права не требуются.

При недоступности Кирилла команда продолжает работу по действующим правилам защиты. Необходимые изменения настроек откладываются до его подключения. Если это задерживает выполнение практики, команда сообщает преподавателю.

## Обоснование решения

1. **Размер команды.** Для четырёх участников достаточно одной основной ветки и отдельных веток задач. GitFlow добавил бы дополнительные операции синхронизации.

2. **Опыт команды.** Команда уже использовала рабочие ветки и PR на первой практике. GitHub Flow позволяет продолжить освоенный процесс и добавить обязательное ревью. GitFlow потребовал бы дополнительных правил работы с develop и release-ветками.

3. **Требования курса.** Обязательные PR и approval другого участника соответствуют выбранному процессу и обеспечиваются защитой main.

4. **Текущее состояние проверок.** Пока CI отсутствует, перед merge выполняются локальный запуск приложения и проверка по инструкции в PR.

5. **Частота релизов.** Фиксированного календаря релизов пока нет, версии готовятся по готовности задач. Поэтому отдельный процесс подготовки регулярных релизов не требуется. Для текущего этапа достаточно проверенной main и отдельных веток задач.

## Последствия

### Положительные (+)

- Для каждой задачи понятны исходная и целевая ветки.
- Изменения проверяются другим участником до попадания в main.
- В PR сохраняются замечания, ответы и история исправлений.
- Не требуется синхронизация нескольких постоянных веток разработки.

### Отрицательные (-)

- Задержка ревью задерживает merge готового изменения.
- До появления CI проверки приложения выполняются вручную.
- Крупные незавершённые функции необходимо разделять на работоспособные части перед включением в main.

### Риски и митигация

| Риск | Вероятность | Влияние | Митигация |
|---|---|---|---|
| Зависимость от одного ответственного за настройки: на практике защиту веток изменяет Кирилл, и его недоступность задержит изменение ruleset | Средняя | Высокое | До занятия подтвердить доступность Кирилла; сохранять актуальные правила в CONTRIBUTING.md; при необходимости привлечь другого уполномоченного администратора организации, а при его отсутствии согласовать перенос с преподавателем |
| Нестабильный код попадёт в main | Средняя | Высокое | Требовать approval другого участника; ревьюер выполняет проверку из PR, запускает приложение и проверяет GET /health |
| PR накапливаются из-за задержек ревью | Средняя | Среднее | Первый ответ ревьюера — в течение 24 часов; при недоступности ревьюера назначить другого участника |
| Конфликты при параллельном изменении файлов | Средняя | Среднее | Делать небольшие PR; получать изменения через git merge origin/main, разрешать конфликты и повторно запрашивать ревью |
